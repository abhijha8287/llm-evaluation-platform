## Problem Statement

Abhishek wants to build an internal-style LLM evaluation platform — the kind of tool
AI companies use to compare, benchmark, and monitor GPT/Claude/Gemini/Llama/DeepSeek/Qwen
against each other on eval metrics (faithfulness, hallucination, toxicity, bias,
latency, cost) — as a portfolio project for AI/ML engineering interviews. This is
not a chatbot and not a startup; it's a demonstration of production-grade eval
system design: async pipelines, clean architecture, correct evaluation methodology.

## What Makes This Cool

Not the UI polish — the engineering depth. The audience is technical interviewers
who will read the code, not just click the demo. The differentiator over
LangSmith/Braintrust/Arize Phoenix/Langfuse isn't "better product" — it's "I built
the internals myself and I understand exactly how faithfulness scoring, async eval
pipelines, and multi-provider abstraction work." Layered on top: an Elo-rated blind
pairwise arena (LMSYS-style) alongside the metric leaderboard, which gives a
concrete, non-generic answer to "why not just use an existing tool."

## Constraints

- Solo build, Windows dev machine, no existing repo or CI yet. Celery has known
  multiprocessing-pool reliability problems on native Windows — the Celery worker
  runs inside a Docker Linux container even during local dev, never natively on
  Windows, to sidestep this entirely.
- Needs real API keys for at least 2-3 model providers to be meaningfully "multi-model"
  (paid: OpenAI/Anthropic/Gemini; free/cheap: Groq or Together for Llama/Qwen, DeepSeek's
  own API is inexpensive). Budget-conscious — eval runs against 6 providers × many
  questions × many metrics gets expensive fast if not rate-limited/sampled deliberately.
  Concrete cap: sample 20-30 questions per dataset per full eval run (not the whole
  dataset every time), target under ~$25/month in API spend during development, and
  only fan out to all 6 providers for demo recordings — day-to-day dev runs against
  2-3 providers.
- Must end in something *deployed and clickable* — a GitHub repo alone doesn't land
  in an interview.
- DeepEval's RAG-family metrics (Faithfulness, Context Precision, Context Recall)
  require a `retrieval_context` per question — they don't apply to open-domain
  Q&A without one. Schema and evaluation-pipeline logic must account for this
  rather than silently computing meaningless scores.
- LLM-as-judge metrics (faithfulness, toxicity, bias) need a named judge model.
  Using the same model family to judge its own answers introduces self-preference
  bias — the judge should be a fixed, separate model (e.g., GPT-4o-mini) used for
  every response regardless of which provider generated it, and this choice should
  be documented in the README as a known limitation, not hidden.
- Target timebox: aim to ship phases 1-7 (core loop through the Promptfoo
  regression engine — see Next Steps) within the active build window; phases 8-9
  (full multi-page dashboard, Prometheus/Grafana) are explicitly optional polish —
  cut them first if time runs short. Phase 10 (deploy) is not optional; a
  half-built system that isn't deployed fails Premise 4.

## Premises

1. This is a portfolio piece for AI/ML interview reviewers — the win condition is
   demonstrated engineering depth, not competing with funded eval-tooling startups. — AGREED
2. Build toward the full original spec (multi-provider, DeepEval+Promptfoo,
   Celery/Redis, Prometheus/Grafana, Next.js dashboard), accepting this is genuinely
   multi-week work. Ragas is dropped: it computes largely the same RAG metrics
   (faithfulness, context precision/recall) that DeepEval already covers, so running
   both adds no differentiation for a portfolio piece — one RAG-metric engine is
   enough. Promptfoo is kept for a distinct job: prompt-version regression testing
   (ties to the PromptVersions/RegressionRuns tables), which DeepEval doesn't do. — AGREED
3. `Questions` need a type flag distinguishing **open-domain** (no context — latency/
   cost/toxicity/bias/relevancy only) from **RAG-style** (context + expected_output —
   full DeepEval RAG metric suite applies). Not every metric applies to every question. — AGREED
4. A live deployed demo is required, not just a repo + README. — AGREED
5. Build in staged, demoable phases (matching the original step-by-step spec) rather
   than attempting the entire system in one shot. — AGREED

## Approaches Considered

### Approach A: Staged core-first
Effort: M → XL over time | Risk: Low
Build a small real slice first — FastAPI + Postgres + LiteLLM + DeepEval, 2-3
providers, one dataset type, deployed — then layer in Celery/Redis, Prometheus/
Grafana, and the full Next.js dashboard across the original 9 phases, each one
demoable before the next starts.
- Pros: always a working deployed artifact; validates schema/API/eval-pipeline
  shape before committing to heavier infra; matches the staged-approval workflow
  already specified.
- Cons: adding Celery later means touching the eval-call code again (sync → async
  task boundary); requires discipline to keep going past the "boring" MVP.
- Reuses: DB schema, LiteLLM abstraction, and DeepEval metric functions carry
  forward unchanged into every later phase — none of this is wasted work.

### Approach B: Full architecture from day one
Effort: XL | Risk: Medium-High
Build toward the complete spec as one continuous effort — all 6 providers, Celery/
Redis, Prometheus/Grafana, full dashboard, all metrics — exactly as originally
specced, no intermediate deployable milestones.
- Pros: no rework; the architecture interviewers eventually see is the real target
  architecture from the start.
- Cons: nothing demoable until several phases deep — the classic solo-portfolio
  failure mode: impressive scaffolding, no live product, high abandonment risk.
- Reuses: n/a — this is the literal spec as given.

### Approach C: Arena/Elo differentiator
Effort: L (on top of A or B) | Risk: Medium
Same core infra as A/B, but add blind pairwise model comparisons + an Elo rating
system alongside the metric-based leaderboard.
- Pros: concrete, specific answer to "why not just use LangSmith"; Elo rating math
  is a self-contained, explainable interview talking point; pairwise blind
  comparisons produce cleaner preference data than absolute LLM-judge scores alone.
- Cons: extra schema/UI scope (Comparisons + Elo tables, pairwise voting UI); Elo
  needs real volume to look statistically meaningful against a small solo-built
  dataset.
- Reuses: everything from A/B; extends rather than replaces the schema.

## Recommended Approach

**A + C combined.** Use Approach A's staged execution order — always ship something
deployable — but treat the full spec (Approach B's target) as the destination, not
a one-shot attempt. Add the Arena/Elo feature (Approach C) as its own phase once the
core evaluation loop works end-to-end. This gets continuous deployable progress
*and* the differentiation story, without Approach B's all-or-nothing risk. This was
your own synthesis, not a menu pick — a good signal (see "What I noticed" below).

## Open Questions

- Which providers get real API keys for v1? (Recommend: OpenAI + Anthropic + one
  free/cheap open-model route via Groq or Together, rather than all 6 from day one —
  cost and rate-limit surface area scales with provider count × dataset size.)
- Dataset content: reuse a known public eval set (e.g., TruthfulQA subset for
  hallucination, a small custom RAG set with real retrieval_context) vs hand-authoring
  a small domain-specific set for a stronger interview narrative? Recommend a mix —
  one public benchmark subset (for credibility) + one hand-authored domain set (for
  a story to tell).
- Hosting for the deployed demo: Fly.io/Render (backend + worker + Postgres + Redis)
  + Vercel (Next.js frontend) is the natural split given the stack — confirm before
  Docker/CI phase.
- Managed Postgres (Neon/Supabase free tier) vs self-hosted in the same deploy —
  managed is simpler for a portfolio project and removes a failure mode.

## Success Criteria

- Deployed, publicly reachable demo URL showing a live leaderboard comparing at
  least 3 real model providers across at least 2 datasets (one open-domain, one
  RAG-style with real retrieval_context).
- At least 4 metrics computed and persisted per response: DeepEval's Faithfulness
  metric (RAG questions only — this IS the platform's hallucination signal:
  contradiction between the answer and the provided retrieval_context), toxicity,
  bias, answer relevancy — plus latency, token usage, and cost tracked on every
  response regardless of type. All LLM-as-judge metrics use a single fixed judge
  model (see Constraints) so scores are comparable across providers.
- Evaluation runs execute asynchronously (Celery workers) — no batch eval blocks
  the API.
- Elo-rated blind arena live alongside the metric leaderboard, with ratings that
  visibly update as comparisons run.
- Pytest suite covering repository layer, evaluation scoring logic, and at least
  one API integration test, passing in CI.
- Public GitHub repo with an architecture diagram, setup instructions, and a demo
  GIF/screenshots in the README.

- **Deployed demo:** backend + worker + Postgres + Redis on Fly.io or Render;

- **CI/CD:** GitHub Actions — run pytest + lint on every push; build and push

- **Repo:** public GitHub repo is the primary artifact recruiters will see —

## Next Steps

Build order (staged, per Approach A+C — each step ships something real, no
placeholder code, stop for review after each per the original spec):

1. Database schema + Alembic migrations (Users, Projects, Datasets, Questions,
   Runs, Models, Responses, EvaluationResults, Metrics, PromptTemplates,
   PromptVersions, RegressionRuns — with the open-domain/RAG-style Question type
   split from Premise 3). Users/Projects exist even though this is a solo demo:
   real JWT auth and project-scoped resources are themselves a portfolio signal
   (multi-tenant SaaS patterns), not vestigial — the demo just seeds one
   user/project by default.
2. Backend core: FastAPI app skeleton, repository pattern, LiteLLM model-runner
   abstraction for 2-3 providers, JWT auth.
3. Evaluation engine v1: DeepEval integration for the metrics that apply to each
   question type; store scores + reasons/explanations.
4. Minimal frontend: leaderboard + run trigger, deployed — first end-to-end
   demoable milestone.
5. Async layer: Celery + Redis for batch evaluation runs; latency/cost/token
   tracking wired through.
6. Arena/Elo feature: pairwise comparison UI + Elo rating computation and storage.
   Vote source is explicit, not left implicit: a fixed neutral LLM judge (same
   model as the metric judge) casts the bulk of blind pairwise votes to reach
   meaningful Elo volume quickly, plus a manual voting UI where you can cast real
   human votes — both write to the same Comparisons table, tagged by voter type,
   so the leaderboard can show LLM-judged vs human-judged Elo separately.
7. Prompt regression engine: Promptfoo integration — versioned prompts stored in
   PromptTemplates/PromptVersions, regression runs re-score a prompt version
   against the existing DeepEval metrics and stored expected outputs, diffing
   against the prior version's scores; results persist to RegressionRuns. This
   is the backend the "Prompt Testing" and "Regression Results" pages (step 8)
   render — a UI-listed feature is not "done" until this step ships.
8. Full dashboard: remaining pages (Projects, Datasets, Model Comparison,
   Experiment History, Prompt Testing, Regression Results, Settings), charts.
9. Monitoring: Prometheus + Grafana wired to the FastAPI/Celery services.
10. Docker Compose finalization + CI/CD + deploy to chosen host + README/docs pass.

**Locked-in architecture decisions (D1-D13):**

1. **Celery/async bridge** — `asyncio.run()` wrapper inside each Celery task; eval/LiteLLM code stays fully async.
2. **Public demo abuse prevention** — read-only public access; trigger-run endpoint rate-limited (e.g. 3 new runs/day) regardless of auth.
3. **Provider failure isolation** — `Response.status` (pending/success/failed/timeout); one failed provider never blocks or corrupts the other N-1.
4. **Elo concurrency** — row-level lock (`SELECT ... FOR UPDATE`) around Elo updates; no dropped updates under concurrent comparisons.
5. **Sample determinism** — fixed, seeded sample per dataset version; every provider scored on identical questions for fair leaderboard comparison.
6. **Pricing data source** — LiteLLM's built-in pricing map (`litellm.model_cost`), not a hand-maintained Costs table.
7. **Regression snapshot** — `RegressionRun` pins a dataset version at creation; mismatched-version comparisons are rejected as "not comparable," never silently diffed.
8. **DRY eval scoring** — one shared `EvaluationService` used by both live eval (Phase 3) and regression re-scoring (Phase 7).
9. **Judge failure status** — `EvaluationResult.status` field; failed judge calls excluded from averages, never counted as a real 0.
10. **Auth model** — login-only with a single seeded demo user for the public deploy; no open self-registration.
11. **Test coverage** — every phase ships its own tests in the same commit as the feature code, no deferral to a follow-up pass.
12. **Task granularity** — one Celery task per (question, provider) pair, not one task per Run, so horizontal worker scaling actually helps.
13. **Leaderboard caching** — Redis cache for leaderboard aggregates, invalidated on new `EvaluationResult` writes.
